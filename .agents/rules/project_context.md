# АРМ «Розклади та Диспетчеризація» — КП «Одесміськелектротранс» (Контекст, Архітектура та Правила)

Цей документ є єдиним джерелом правди (Single Source of Truth) щодо бізнес-логіки, архітектури, структури кодової бази, стеків технологій та правил дизайну проекту автоматизованого робочого місця (АРМ) КП «Одесміськелектротранс» (ОМЕТ).

---

## 1. Загальний опис системи

**АРМ «Розклади та Диспетчеризація»** — це комплексне enterprise-рішення для планування графіків руху, оперативного диспетчерського керування (CAD/AVL), добової рознарядки водіїв, онлайн-моніторингу трамваїв/тролейбусів міста Одеси та взаємодії з бортовими терміналами водіїв.

### Основні групи користувачів:
1. **Інженер-графіст (Відділ розкладів)**: створення еталонних розкладів, ручне задання кількості нарядів з розрахунком результуючого інтервалу, розрахунок обідів та пересадок, друк зведених сіток та маршрутних книжок під А4.
2. **Черговий диспетчер (Центральна диспетчерська / Лінійні диспетчери)**: оперативний контроль відхилень ($\pm\Delta t$), ліквідація «паровозиків» (спарювання), видача електронних розпоряджень (Short Turn, Pacing, заміна вагонів, об'їзди), контроль повітряних тривог.
3. **Керівництво та аналітики**: оперативні KPI, звіти регулярності (On-Time Performance — OTP), статистика виконання плану перевезень.
4. **Адміністратор системи**: ведення довідників мережі (зупинки, маршрути, депо, колійні стрілки, пункти обіду, точки примикання до депо), керування доступом (RBAC).

## 2. Залізні правила математичного ядра та розрахунку розкладів (ОМЕТ Core Rules)

1. **Ручне задання кількості нарядів ($N$) та розрахунок інтервалу ($I$)**:
   - Спеціаліст служби руху **вручну вказує кількість випусків (нарядів) $N$** на маршрут (наприклад, 14 вагонів на маршрут №5).
   - Математичне ядро на основі заданого часу оборотного рейсу ($T_{\text{об}} = t_{\text{туди}} + t_{\text{назад}} + 2 \times t_{\text{відст}}$) розраховує **результуючий інтервал руху $I = T_{\text{об}} / N$** та адаптує нормативні відстої на кінцевих у діапазоні **5 — 10 хвилин**.

2. **Правила надання обідів (Lunch Allocator)**:
   - **Нормативна базова тривалість**: 15 хв (трамвай) / 20 хв (тролейбус).
   - **Автоматичний адаптивний розрахунок**: система динамічно вираховує обідній час відповідно до розрахункового інтервалу на маршруті ($I = T_{\text{об}} / N$) для збереження тактового розкладу на лінії.
   - **Вікно надання**: суворо між **4-ю та 6-ю годиною** роботи зміни водія.
   - **Місце обіду**: виключно на **Диспетчерських пунктах (ДП)** / кінцевих станціях з кімнатами відпочинку та їдальнями (ДП «вул. Паустовського», ДП «Станція Аркадія», ДП «Куликове поле», ДП «вул. Архітекторська»).
   - **Обіди для двозмінних нарядів**: обов'язковий обід для водія І зміни (між 10:30 і 12:30) та окремий обід для водія ІІ зміни (між 17:30 і 19:30).
   - **Обіди для розривних нарядів**: обов'язковий обід для водія І зміни (Вагон 1) та окремий обід для водія ІІ зміни (Вагон 2).
   - **Обов'язкова компенсація робочого часу**: якщо автоматизована система призначає розширений час обіду (наприклад, 25, 30 чи 35 хв замість 15/20 хв для узгодження графіка), увесь понаднормовий час ($\Delta T_{\text{overtime}} = T_{\text{lunch}} - T_{\text{base}}$) **обов'язково додається до загальної тривалості зміни водія**.

3. **Справжні розривні наряди (Hot-Swap / Ротація 2-х вагонів)**:
   - Під одним номером розривного наряду працюють **2 фізично різних вагони** та 2 водії.
   - **Вагон 1 (І зміна)**: відпрацьовує $\le 10$ годин (в середньому $\approx 7.5\dots8.5$ год) з обідом $\to$ доїжджає до **найближчої зупинки маршруту до депо (вузол сходження)** $\to$ заїжджає в депо на щоденне ТО/огляд.
   - **Вагон 2 (ІІ зміна)**: виїжджає з депо $\to$ підхоплює наряд на цій же **найближчій зупинці маршруту до депо** $\to$ відпрацьовує зміну ІІ з обідом $\to$ ввечері заїжджає в депо.

4. **Матриця нульових рейсів, Мультидепо та топологія депо Одеси**:
   - **Трамвайні маршрути (16 діючих маршрутів):** №1, 5, 6, 7, 10, 11, 12, 13, 15, 17, 18, 20, 21, 26, 27, 28 (маршрут №3 відсутній / поглинуто магістраллю №7 «Північ-Південь»).
   - **Тролейбусні маршрути (7 діючих маршрутів):** №2, 3, 7, 8, 9, 10, 12 (маршрут №14 відсутній).
   - **Тролейбуси**: виключно **Тролейбусне депо №1** (вул. Інглезі). Тролейбусне депо №2 відсутнє на балансі підприємства та вилучено з усіх баз даних.
   - **Трамваї (Мультидепо)**: випуск вагонів може здійснюватися як з **ТД-1** (вул. Водопровідна), так і з **ТД-2** (Слобідка, вул. Воробйова). Кожному наряду маршруту може призначатися індивідуальне депо виїзду.
   - Для кожного наряду нормативний час слідування ($t_{\text{нул}}$), відстань ($L_{\text{нул}}$) та вузол примикання розраховуються динамічно через `deadhead_optimizer` та топологічну матрицю `ODESSA_DEPOT_ZERO_RUN_MATRIX`, а закріплене депо зберігається в колонці `depot_id` таблиці БД `static_duties`.
   - Водій бере пасажирів під час виконання нульового рейсу.
   - Час явки водія = Час виїзду з воріт депо $- 10$ хв (трамвай) / $- 19$ хв (тролейбус) на передрейсовий огляд вагона.

5. **Синхронізація спільних ділянок («Зв'язок»)**:
   - Автоматичне рівномірне розведення рейсів різних маршрутів на спільних коридорах (наприклад, трамваї №1 та №7 на Добровольського; тролейбуси №7 і №9 на пр. Шевченка) для уникнення одночасного прибуття.

6. **Суворе розділення обов'язків модулів планування (No Auto-Generation in Grid View)**:
   - **Єдине місце генерації**: Налаштування кількості випусків, типів змін, індивідуальних депо та кінцевих станцій, а також генерація і первинне затвердження графіка відбуваються **виключно у вкладці «Параметри та конструктор нарядів» (`/planning/parameters`)**.
   - **Зведена шахова таблиця (`/planning/matrix`)**: Призначена виключно для перегляду, фільтрації, друку форм А4 та експорту вже затвердженого графіка. Будь-яка фонова чи автоматична генерація розкладу за відсутності даних **заборонена**. Кнопка «Оновити» вилучена. Якщо для маршруту ще немає графіка, відображається інформативний Empty State з прямим переходом до конструктора нарядів.

7. **Гарантоване збереження типів нарядів (Universal Key Resolver)**:
   - Синхронізація конфігурацій між фронтендом і бекендом забезпечується резолвером ключів (`1..N`, `route_id-0X`, `0X`), що гарантує 100% відповідність затверджених типів (`DOUBLE`, `SINGLE`, `SPLIT`, `PEAK`) без примусового переведення у розривні (`SPLIT`).

Підсистема планування розкладів складається з 8 чітко розмежованих модулів із єдиною синхронізацією стану (`useScheduleStore`):

   - Покроковий сценарний майстер (Етап 1: Макро-параметри, вибір дат, розрахунок інтервалу $I = T_{\text{об}} / N$; Етап 2: Індивідуальне коригування нарядів).
   - Індивідуальний вибір депо виїзду для кожного наряду (Мультидепо: ТД-1 / ТД-2 для трамваїв) та гарантована передача типів нарядів без спонтанних розривів.

   - Переміщення нарядів кнопками `↑` / `↓` для гнучкого налаштування черговості виходу зі збереженням нумерації `1..N`.
   - Групове копіювання параметрів першого наряду до всіх.
   - Підсистема збереження та завантаження **Чернеток (Drafts)** і автоматичне збереження в **Архів розкладів**.
2. 📊 **Зведена шахова таблиця рейсів (`/planning/matrix`)**:
   - Офіційний розрахунковий документ А4 Landscape: паспорт показників + повна матриця всіх рейсів 1..22+ із позначками обідів `[О-15]`, `[О-20]`, `[О-30*]`, перезмінок та ротацій.
   - Закріплення колонок (`sticky left`): «№ наряду», «Тип», «Депо» (з параметрами нульового слідування) та «Станція виходу».
   - Суворий захист від випадкового перерахунку: відсутність руйнівних кнопок перерахунку та автогенерації розкладу; відображення Empty State з кнопкою переходу до конструктора, якщо розклад ще не створено.
   - Швидкі фільтри за типами нарядів (Всі, Двозмінні, Однозмінні, Розривні, Пікові), пошук за номером наряду та експорт в Excel (.csv).
3. 📍 **Рейси за Контрольними Точками (`/planning/control-points`)**:
   - Погодинна сітка відправлень за ключовими кінцевими та проміжними КТ.
4. ⏱️ **Ґантта Статичних Нарядів (`/planning/gantt`)**:
   - Візуальна часова шкала добового графіка руху вагонів та обідів.
5. ✂️ **Конструктор Змін & КПЗ (`/planning/shifts`)**:
   - Розрізання змін водіїв (Run Cutting) та підготовка карток КПЗ.

7. 📖 **Маршрутна книжка водія (`/planning/driver-book`)**:

## 6. Підсистема «Аналітика, Звітність та Регулярність (OTP)»

Модуль відповідає за стратегічний та оперативний аналіз надійності перевезень КП «Одесміськелектротранс»:

1. 🎯 **Єдина математична модель On-Time Performance (OTP)**:
   - **Норматив пунктуальності**: Прибуття на зупинку / Контрольну Точку з відхиленням у межах $\Delta t \in [-2.0; +2.0]$ хвилин відносно еталонного розкладу.
   - **Зважений розрахунок Network OTP**: Розраховується строго з урахуванням ваги маршруту (кількості зафіксованих точок проходження $R_i$):
     $$\text{Network OTP} = \frac{\sum_{i=1}^{M} (\text{OTP}_i \times R_i)}{\sum_{i=1}^{M} R_i}$$
   - **Захист від граничних випадків (Edge Cases)**: Автоматична валідація ділення на нуль (`0 records`) з безпечним відображенням `0.0%` замість `NaN%`.

2. 🗄️ **Синхронізація з базою даних PostgreSQL**:
   - **Таблиця `eta_logs`**: Реєстрація кожної пройденої контрольної точки з полями `vehicle_id`, `route_id`, `stop_id`, `deviation_min`, `recorded_at`.
   - **Таблиця `incident_logs`**: Журнал оперативних інцидентів (ДТП, обриви контактної мережі, сходи з рейок) зі статусами `NEW`, `IN_PROGRESS`, `RESOLVED`.
   - **Ендпоінти REST API**:
     - `GET /api/v1/analytics/daily-performance?target_date=YYYY-MM-DD` $\to$ Масив `RoutePerformance[]`
     - `GET /api/v1/analytics/incidents-summary?target_date=YYYY-MM-DD` $\to$ Об'єкт `IncidentStats`
     - `GET /api/v1/analytics/kpi` $\to$ Загальні системні показники випуску та інтервалів.

3. 🖥️ **Компоненти та інтерфейси модуля**:
   - 📈 **Головний Дашборд KPI (`/`) — `ExecutiveDashboardView.tsx`**:
     - 4 оперативні картки KPI (Активні маршрути, Добовий обсяг рейсів, Конфлікти вузлів, Дотримання КЗпП водіями).
     - Динамічний розрахунок відсотка готовності випуску.
     - Центр оперативних повідомлень та конфліктів із категоріями (конфлікти паровозності, норми КЗпП, відтяжки, GTFS-інтеграція).
     - Повна сумісність із темною темою диспетчерської `night-dispatch`.
   - 📑 **Звітність регулярності руху (`/analytics`) — `AnalyticsReportView.tsx`**:
     - Порівняльна гістограма OTP та середніх запізнень за маршрутами (Recharts).
     - Кругова діаграма стану ліквідації інцидентів.
     - Зведена таблиця надійності маршрутів із кольоровою градацією (Оптимально $\ge 80\%$, Потребує уваги $60\dots79\%$, Критично $<60\%$).
     - Експорт звіту у формат **CSV** через UTF-8 BOM `Blob` та оптимізований друк під формат А4.
   - 🪟 **Модальний аналітичний звіт — `AnalyticalReportModal.tsx`**:
     - Швидкий доступ до OTP-аналітики з шапки АРМ у будь-якому робочому просторі.
     - Повна доступність за стандартом **WCAG 2.1 AA** (закриття по `Escape`, фокус-менеджмент, клік на бекдроп, `aria-modal="true"`).

4. 📡 **Телеметрія живого флоту (`useTelemetryStore`)**:
   - O(1) словникова нормалізація бортів (`Record<string, VehicleTelemetry>`).
   - Автоматична фіксація статусу з'єднання `isConnected` при мережевих збоях.
   - Відсутність жорстких магічних чисел при нічному черговому випуску.

## 7. Підсистема «Оперативна Диспетчерська (CAD/AVL, Wialon GIS та Журнал Розпоряджень)»

Модуль реалізує цілодобове керування рухом міського електротранспорту КП «Одесміськелектротранс» у реальному часі:

1. 🗺️ **Карта Руху (Wialon Live GIS & Simulation) — `/dispatch/map` (`LiveMapView.tsx`, `TelemetryMarkers.tsx`)**:
   - **Високопродуктивний рендеринг**: Кешування DOM-посилань маркерів вагона без викликів `marker.setIcon()` для усунення Garbage Collection spikes та витоків пам'яті при 100+ активних ТЗ.
   - **Інтерполяція координат (60 FPS)**: Кінематичне згладжування (Dead Reckoning) до 3.5 сек між пакетами GPS.
   - **Полігони депо та геозони**: Точні периметри ТД-1 (Водопровідна), ТД-2 (Слобідка) та ТрД (Інглезі).
   - **Нормативи колірної індикації КП «ОМЕТ»**:
     - 🔴 **Нагін / Поспіх ($> +2.0$ хв)**: Червоний пульсуючий індикатор (грубе порушення ПТЕ та безпеки руху).
     - 🟡 **Запізнення (від $-3.0$ до $-7.0$ хв)**: Бурштиновий індикатор (експлуатаційна затримка).
     - 🔴 **Критичне запізнення ($< -7.0$ хв)**: Червоний індикатор.
     - 🟢 **У графіку (від $-3.0$ до $+2.0$ хв)**: Зелений індикатор нормативного руху.
     - ⚪ **Втрата зв'язку ($> 120$ сек)**: Сірий напівпрозорий індикатор.

2. 📊 **CAD/AVL Матриця та Відхилення — `/dispatch/matrix` (`DispatcherLiveView.tsx`)**:
   - **Фіксація першого стовпця (`sticky left`)**: Стовпець «Борт / Тип» залишається закріпленим при горизонтальному скролі таблиці контрольних точок.

## 9. Довідники інфраструктури, Автентифікація (RBAC) та Захист інтерфейсу

1. 🗂️ **Довідники інфраструктури мережі (`NetworkSettingsTab.tsx`)**:
   - **Маршрути (`RouteFormModal.tsx`)**: Управління маршрутами трамваїв/тролейбусів з обов'язковою валідацією довжини напрямків ($0.1 \le L \le 100$ км), терміналів та розрахунком швидкості сполучення $V_{\text{сп}} = (L / T) \times 60$.
   - **Зупинки та КТ (`AdminStopsManager.tsx`)**: Повний реєстр зупинок, прив'язка GPS-координат міста Одеси, маркування диспетчерських контрольних точок (КТ) та експорт/імпорт.
   - **Колійні Вузли / Розв'язки (`GlobalHubFormModal.tsx`)**: Задання колійних каналів відстою, місткості ($1 \le C \le 20$ ТЗ) та мінімального інтервалу безпеки ($1 \le h_{\text{min}} \le 60$ хв).
   - **Пункти Обіду (`BreakLocationFormModal.tsx`)**: Регламентація місць прийому їжі на ДП та кінцевих з контролем тривалості за нормами КЗпП України ($15 \le T_{\text{обід}} \le 120$ хв).
   - **Депо та геозони (`AdminDepotsManager.tsx`)**: Налаштування ТД-1, ТД-2 та Тролейбусного депо №1.

2. 🔐 **Безпека, Авторизація та Захист маршрутів (RBAC)**:
   - **Стандарт токенів**: OAuth2 + Bearer JWT (термін дії сесії — 10 годин).
   - **`ProtectedRoute.tsx`**: Гарантована перевірка наявності валідного токена із миттєвим перенаправленням на `/login` у разі завершення сесії без «білих екранів».
   - **`SuperuserRoute.tsx`**: Суворий захист панелі конфігурації та системного адміністрування (`is_superuser: true`), виключення side-effects під час фази рендеру (використання `useEffect`).
   - **`AuthLoginView.tsx`**: Повна сумісність з бекендом FastAPI (`/api/v1/auth/login`), перемикач видимості пароля (`Eye` / `EyeOff`), підтримка автозаповнення форм (`autoComplete`) та швидкі демо-профілі.

3. 🎨 **Уніфікована система тем (`omet-clean` / `night-dispatch`)**:
   - Синхронізоване керування через `Header.tsx`, `useScheduleStore` та `useSettingsStore` з підтримкою збереження в `localStorage` (`omet_theme`).

   - Меню навігаційних груп `NAV_GROUPS` захищене обмеженням `max-h-[calc(100vh-140px)] overflow-y-auto` для коректного відображення на компактних екранах (768px висоти).

## 10. Синхронізація структур даних, Бази даних та API Клієнта

1. **Моделі розкладів та нарядів (Multi-Depot Synchronization)**:
   - Таблиця бази даних `static_duties` містить колонку `depot_id (VARCHAR)` для фіксації прив'язки кожного наряду до конкретного фізичного депо (`depot_1`, `depot_2`, `depot_3`).
   - SQLAlchemy модель `StaticDuty` (`backend/app/models/schedule.py`) та Pydantic схема `StaticDutyResponse` (`backend/app/schemas/schedule.py`) містять атрибути `depot_id: Optional[str]` та `route_id: Optional[str]`.
   - TypeScript інтерфейс `DriverDuty` (`src/types/index.ts`) підтримує `depotId?: string` та `routeId?: string | number`, забезпечуючи 100% двосторонню сумісність між клієнтом та бекендом.

2. **Мережева адресація та стійкість API (`src/utils/apiClient.ts`)**:
   - Функція `getBaseUrl()` у браузері автоматично визначає локальне середовище (`localhost` / `127.0.0.1`) та надсилає запити безпосередньо на порт `8000` (`http://localhost:8000/api`).
   - Це усуває залежність від внутрішнього проксі Node.js у Vite, виключаючи блокування `EPERM` та випадкові помилки `500 Internal Server Error`.
   - Ендпоінти авторизації `/auth/login` та `/auth/me` обробляють власні помилки (400, 401) без викидання глобальних сповіщень про розрив сесії для неавторизованих користувачів.
